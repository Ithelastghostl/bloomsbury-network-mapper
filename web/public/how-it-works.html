Overview

What the platform is

The Network Mapper is a read-only dashboard over a graph of people and organisations connected to Bloomsbury Football Foundation. It answers three questions: who are the high-net-worth individuals around us, how are they connected, and what is the warmest route to reach them.

Everything on screen is data already stored in the database. The dashboard displays; it does not run enrichment on its own. Its one action, Augment & Persist, only ever runs when a person clicks the button. Nothing fires automatically in the background.

Foundations

The data model

All data lives in a Supabase Postgres database under the app schema. The dashboard reads a handful of core tables:

TableWhat it holds
canonical_entitiesThe master list of every person and company — id, display name, type, and a flexible attributes field (where wealth data and flags are stored).
wealth_estimatesWealth assessments per entity: a band, a score, a confidence, and structured evidence.
enrichment_evidenceSupporting evidence rows — source, layer, text, URL, confidence — backing a wealth or status claim.
network_connectionsDirected relationships between two entities (person→person and person→company), with a type and the organisation that links them.
co_director_edgesPeople who share a company board, sourced from Companies House filings.

When a page needs to show people, it loads their canonical records and then calls enrichEntities(), which fetches wealth, evidence and connections for the whole batch in parallel and stitches them together into an EnrichedEntity — the shape every screen renders from.

The funnel

Seeds → Leads → Pipeline → All

People are sorted into four buckets. This is the spine of the whole tool: it separates who we already have from who we’ve discovered around them.

Seeds the people we already have

The original supporter and target list: the people the project started from, each with research reports and the prompts behind them. Membership is defined by name. A curated list of 323 seed people (from the HNW and supporter spreadsheets) ships with the app as seed-people.json, and a person is a seed when their name matches that list via isSeedPerson(). That match normalises names — lowercases them, strips titles like Sir/Dr and honours like CBE — so spelling variants still resolve. About 318 of the 323 are now in the database; the handful left are personal contacts of the founder with no public record to research.

Leads discovered & already enriched

People we found through the seeds (co-directors, fellow trustees, family) who are not seeds themselves but already carry a wealth estimate or evidence. Filter: !isSeedPerson() && (has wealth OR has evidence). These are the warm prospects.

Pipeline discovered, not yet researched

Discovered non-seed people with no wealth or evidence yet — the raw backlog awaiting research. Filter: !isSeedPerson() && no wealth && no evidence.

All everyone

Every person entity, unfiltered. The complete view.

The buckets are a clean partition. Seeds + Leads + Pipeline = All — no person is counted twice, none is missed.

Signals

Wealth & evidence

Each person can carry a wealth band — the headline signal used for prioritisation and sorting:

£100M+ £25M–100M £5M–25M £1M–5M Unknown

A band is backed by a score (0–1), a confidence (0–1), an estimated net worth in GBP, a source of wealth, and a written summary with citations. The portfolio summary on the Leads view aggregates these — combined & average net worth, band distribution, and the best-connected people — to give a one-glance read on a whole list.

Connections

The relationship graph

There are three graph views, each answering a different question.

Orbit — how people cluster

The Orbit view draws an edge between two people whenever they share something. It builds those person-to-person links from three sources, then merges duplicates:

  • Direct relationships — existing person→person links (co-director, family member, co-trustee, associate).
  • Shared company — if two people are both attached to the same company, they’re linked (the company is collapsed into a direct bond). Companies with more than 50 members are skipped so a giant employer doesn’t create a hairball.
  • Shared boards — Companies House co-director records.

Each resulting bond carries a weight = the number of distinct reasons two people are linked, so stronger ties draw thicker. Nodes are coloured by community (connected-component), which is what turns a scattered cloud into readable clusters. A toggle switches to “+ Institutions” (bipartite) mode, which puts companies back in as visible connector nodes so you can see which organisation links a group.

Institutions — individuals & companies

People linked to the (non-charity) companies they direct or advise — boards and directorships.

Charities — charities at the centre

People linked to charities and foundations, surfacing trustees and supporters. A company counts as a charity if its name contains words like foundation, trust, charity, charitable, endowment, or it has Charity Commission evidence — more reliable than keywords alone.

Why the graph looks connected now. The underlying relationships were always there. The earlier view dropped the shared-board edges and used weak layout forces, so it rendered as scattered dots. Folding in co-directorships and shared companies, then colouring by community, reveals the single large network underneath — most people sit in one connected map.

Enrichment

The wealth augmentation loop

Research is done by a local Claude Code agent using web search — there is no API key in the app and the dashboard never calls a model itself. Instead it acts as the queue and the store. The loop:

  1. Request — On a Lead’s detail page, a user clicks Augment & Persist. This sets augmentation_requested on that person. (Explicit click only — nothing auto-fires.)
  2. Queue — The person now appears in GET /api/crm/augment-queue, returned in the exact shape the research tooling expects.
  3. Research — The local agent reads the queue and researches each person via web search (net worth, source of wealth, evidence with citations).
  4. Persist — The agent POSTs results to /api/entities/{id}/augment. The server writes evidence, upserts the wealth estimate, and stamps wealth_augmented_at — which removes the queue flag and promotes the Lead into a Seed-quality profile.

The write endpoints are admin-gated. For local use a CRM_LOCAL_MODE flag bypasses that gate (only when not in production), so the tethered agent can persist without a login.

Under the hood

Stack & rendering

  • Next.js (App Router) with React Server Components — pages fetch from Supabase on the server.
  • Supabase Postgres (schema app) accessed with a service-role client; every request has an 8-second timeout with retries so a flaky connection fails fast instead of hanging, and pages degrade to a friendly error card rather than crashing.
  • D3 for the force-directed graph; the layout is computed and then frozen, so nodes settle and stop rather than drifting forever.
  • The CRM is rendered per request (never prerendered at build), so it always reflects current data and the build never depends on the database.
  • Styling is a light theme — Bloomsbury gold on white — applied through CSS design tokens.
